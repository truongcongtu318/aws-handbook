1. VPC & Mạng Cơ Bản (Networking Fundamentals)

Amazon Virtual Private Cloud (VPC)
Domain 1 & 2 (Core)

📖 Lý thuyết cốt lõi & Bản chất kiến trúc:

  • Bản chất: Là một mạng riêng ảo biệt lập về mặt logic trên Cloud của AWS, tương tự trung tâm dữ liệu truyền thống nhưng hoàn toàn ảo hóa.
  • Phạm vi: VPC thuộc cấp Region. Một VPC trải rộng trên tất cả các Availability Zones (AZs) trong Region đó.
  • CIDR Block: Quy định dải IP riêng (RFC 1918), kích thước từ /16 (65,536 IPs) đến /28 (16 IPs). Không thể mở rộng hay thu hẹp dải CIDR chính sau khi tạo (nhưng có thể add thêm secondary CIDR).
  • Subnets: Mỗi Subnet nằm trọn vẹn trong đúng 1 Availability Zone duy nhất. AWS luôn dành riêng 5 địa chỉ IP đầu và cuối trong mỗi Subnet (ví dụ subnet /24 có 256 IP thì chỉ khả dụng 251 IP).
  • Public vs Private Subnet: Subnet nào có Route Table trỏ 0.0.0.0/0 ra Internet Gateway (IGW) là Public Subnet. Subnet không trỏ ra IGW là Private Subnet.
⚖️ So sánh kinh điển: Security Group (SG) vs Network ACL (NACL)
Học Đặc tính Security Group (SG) Network ACL (NACL)
Cấp độ gắn Cấp Instance / Card mạng ảo (ENI) Cấp Subnet (bảo vệ toàn bộ máy trong subnet)
Trạng thái (State) Stateful (Cho phép Inbound thì Outbound tự động mở) Stateless (Phải cấu hình tường minh cả Inbound & Outbound Ephemeral Ports 1024-65535)
Loại Rule Chỉ có rule ALLOW (mặc định deny hết) Có cả rule ALLOW và DENY (chặn IP cụ thể được)
Thứ tự đánh giá Tất cả các rule được đánh giá đồng thời Đánh giá tuần tự theo số thứ tự từ nhỏ đến lớn (Rule 100 Deny sẽ chặn trước Rule 200 Allow)
⚖️ So sánh: VPC Gateway Endpoint vs Interface Endpoint (PrivateLink)
  • Gateway Endpoint: Cấu hình qua Route Table, hoàn toàn miễn phí, chỉ hỗ trợ đúng 2 dịch vụ: Amazon S3 và Amazon DynamoDB.
  • Interface Endpoint (PrivateLink): Tạo ra 1 card mạng ảo (ENI) với Private IP bên trong subnet, tính phí theo giờ và dung lượng, hỗ trợ hầu hết các dịch vụ AWS còn lại (SQS, SNS, KMS, CloudWatch, SSM...).
Học Yêu cầu / Tình huống trong đề thi Tùy chọn / Giải pháp chính xác Bẫy & Lưu ý mấu chốt
EC2 trong Private Subnet cần ra Internet tải update nhưng cấm chiều ngược lại Đặt NAT Gateway ở Public Subnet NAT Gateway bắt buộc phải nằm ở Public Subnet và gắn Elastic IP. Để High Availability, phải tạo 1 NAT Gateway trên mỗi AZ.
Truy cập S3 / DynamoDB từ EC2 Private mà không tốn tiền NAT Gateway Tạo VPC Gateway Endpoint Miễn phí 100%, không đi qua Internet hay NAT Gateway. Thêm prefix list vào Route Table.
Ghi lại vết lưu lượng IP, cổng, gói tin ACCEPT/REJECT trong VPC để kiểm toán Bật VPC Flow Logs Đẩy log về CloudWatch Logs hoặc lưu trữ lâu dài ở Amazon S3.
Nối 2 VPC với nhau không cần đi qua Internet công cộng Tạo VPC Peering Không hỗ trợ chuyển tiếp (No transitive routing): A nối B, B nối C thì A không tự thông C. Dải CIDR không được trùng nhau.
Kết nối hình sao (Hub-and-Spoke) hàng chục VPC và mạng On-premise Dùng AWS Transit Gateway Hỗ trợ Transitive routing, hỗ trợ Multicast, gom toàn bộ kết nối VPC, VPN và Direct Connect về một hub trung tâm.
⚠️ BẪY ĐỀ THI: Khi đề bài hỏi "EC2 in private subnet needs to access S3 with the lowest cost": Luôn chọn Gateway Endpoint, không chọn NAT Gateway vì NAT Gateway tốn phí hourly + data processing.

2. Compute & Scaling (Amazon EC2 & Auto Scaling)

Amazon EC2 (Elastic Compute Cloud)
Domain 3 & 4 (Compute Core)

📖 Lý thuyết cốt lõi & Các mô hình định giá (Purchasing Options):

  • On-Demand: Trả theo giây/giờ. Phù hợp: Ứng dụng mới, tải ngắn hạn, không dự đoán trước được lưu lượng, môi trường dev/test.
  • Compute Savings Plans: Cam kết chi tiêu ($/giờ) trong 1 hoặc 3 năm. Tiết kiệm tới 72%. Linh hoạt nhất: áp dụng cho mọi instance family, hệ điều hành, Region và cả Fargate / Lambda.
  • Spot Instances: Rẻ nhất (giảm tới 90%), tận dụng tài nguyên dư thừa của AWS. Có thể bị thu hồi bất cứ lúc nào với cảnh báo trước 2 phút. Dùng cho: Batch processing, encode video, CI/CD runner, Big Data EMR task nodes. Tuyệt đối không dùng cho Database hoặc Web app phục vụ khách hàng trực tiếp.
  • Dedicated Hosts: Thuê cả server vật lý chuyên dụng. Dùng khi: Bring-Your-Own-License (BYOL) (cần kiểm soát số socket/core theo bản quyền phần mềm) hoặc tuân thủ quy chuẩn pháp lý cách ly phần cứng.
⚖️ So sánh: 3 loại Placement Groups (Nhóm vị trí máy chủ)
  • Cluster: Gom các EC2 nằm sát nhau trên cùng 1 rack vật lý trong 1 AZ $\rightarrow$ Đạt thông lượng mạng cao nhất, độ trễ cực thấp (dùng cho HPC, Machine Learning, Deep Learning).
  • Spread: Rải mỗi EC2 sang 1 rack vật lý hoàn toàn riêng biệt (tối đa 7 máy/AZ) $\rightarrow$ Giảm rủi ro hỏng phần cứng, dùng cho số ít máy chủ tối quan trọng (Critical DB, Master nodes).
  • Partition: Chia các EC2 vào các phân vùng độc lập (mỗi partition chứa nhiều máy nhưng không chung rack với partition khác) $\rightarrow$ Dùng cho hệ thống dữ liệu lớn: Hadoop, Kafka, Cassandra.
Học Yêu cầu / Tình huống trong đề thi Tùy chọn / Giải pháp chính xác Bẫy & Lưu ý mấu chốt
Chống tấn công SSRF đánh cắp quyền IAM Role từ EC2 metadata Bật IMDSv2 (HttpTokens=required) Bắt buộc client phải lấy Session Token trước bằng lệnh HTTP PUT trước khi đọc metadata 169.254.169.254.
Tạm dừng EC2 khi khởi tạo/terminate để chạy script sao lưu log Auto Scaling Lifecycle Hooks Đưa instance vào trạng thái Pending:Wait hoặc Terminating:Wait trước khi hoàn tất vòng đời.
Tự động duy trì mức CPU trung bình của cụm ở mức 50% Auto Scaling Target Tracking Policy AWS tự tính toán số máy cần tăng/giảm dựa trên metric chỉ định (CPU, Request count).
Tắt máy ảo và khởi động lại ngay tức thì mà không phải load lại OS Bật EC2 Hibernation Lưu dữ liệu trong RAM vào ổ EBS root volume khi hibernate.

3. Containers & Serverless (ECS, EKS, Fargate, Lambda)

AWS Fargate vs ECS / EKS & AWS Lambda
Domain 3 & 4 (Serverless)

📖 Lý thuyết cốt lõi & So sánh kiến trúc:

  • AWS Fargate: Serverless compute engine cho Docker Containers. Bạn chỉ định nghĩa dung lượng CPU/RAM cho Task, AWS tự động cấp phát và chạy. Hoàn toàn không cần quản lý, vá lỗi hay bảo trì cụm máy chủ EC2 bên dưới $\rightarrow$ Là đáp án vàng cho từ khóa "Containers with least operational overhead".
  • EC2 Launch Type: Bạn tự quản lý cụm EC2 chạy ECS Agent. Dùng khi cần kiểm soát loại máy chuyên biệt (GPU, ARM), gắn ổ đĩa EBS cố định, hoặc tối ưu chi phí với Spot.
  • AWS Lambda: Serverless Event-driven compute. Chỉ chạy khi có event kích hoạt. Tối đa thời gian chạy là 15 phút (900 giây). Tự động scale từ 0 lên hàng chục nghìn lượt chạy song song.
Học Yêu cầu / Tình huống trong đề thi Tùy chọn / Giải pháp chính xác Bẫy & Lưu ý mấu chốt
Triệt tiêu hiện tượng khởi động chậm (Cold Start) của hàm Lambda Bật Provisioned Concurrency Khởi tạo sẵn một số container thực thi ở trạng thái nóng 24/7 để đáp ứng tức thì.
Hàng nghìn hàm Lambda đồng thời làm quá tải sập Database Cấu hình Reserved Concurrency hoặc dùng RDS Proxy Reserved Concurrency giới hạn trần số instance Lambda tối đa; RDS Proxy gom connection pool.
Cho phép Lambda truy cập Database/Cache trong Private Subnet Gán VPC Configuration cho Lambda Yêu cầu IAM Role của Lambda phải có quyền AWSLambdaVPCAccessExecutionRole để tạo ENI trong Subnet.
Deploy code web app không cần dựng hạ tầng, vẫn xem được cấu hình máy chủ Dùng AWS Elastic Beanstalk PaaS hỗ trợ Java, .NET, Node, Python... Triển khai kiểu Immutable hoặc Blue/Green để zero downtime.

4. Amazon S3 & Object Storage Toàn Tập

Amazon Simple Storage Service (S3)
Domain 1, 2, 4 (Storage Core)

📖 Lý thuyết cốt lõi & 8 Lớp lưu trữ (Storage Classes):

  • Bản chất: Lưu trữ hướng đối tượng (Object Storage), không giới hạn dung lượng, kích thước 1 file từ 0 byte đến tối đa 5 TB. Độ bền (Durability) 99.999999999% (11 số 9) trên mọi storage class (trừ One Zone-IA).
  • S3 Standard: Dữ liệu truy cập thường xuyên, độ trễ mili-giây, đa vùng (Multi-AZ).
  • S3 Standard-IA (Infrequent Access): Lưu trữ rẻ hơn, nhưng tính phí khi đọc (retrieval fee). Lưu tối thiểu 30 ngày.
  • S3 One Zone-IA: Chỉ lưu trên 1 AZ duy nhất, rẻ hơn Standard-IA 20%. Mất dữ liệu nếu AZ đó bị hủy diệt. Dùng cho bản backup thứ 2 có thể tạo lại được.
  • S3 Glacier Instant Retrieval: Lưu trữ lâu dài, truy xuất chỉ vài lần/năm nhưng lấy lại dữ liệu trong mili-giây. Lưu tối thiểu 90 ngày.
  • S3 Glacier Flexible Retrieval: Lấy dữ liệu theo 3 tốc độ: Expedited (1-5 phút), Standard (3-5 giờ), Bulk (5-12 giờ - miễn phí). Lưu tối thiểu 90 ngày.
  • S3 Glacier Deep Archive: Lớp lưu trữ rẻ nhất thế giới, dùng cho dữ liệu tuân thủ pháp lý lưu 7-10 năm. Lấy dữ liệu: Standard (12 giờ), Bulk (48 giờ). Lưu tối thiểu 180 ngày.
  • S3 Intelligent-Tiering: Tự động luân chuyển giữa các tier dựa trên thói quen đọc mà không mất phí truy xuất dữ liệu. Tốt nhất khi không rõ chu kỳ sử dụng.
  • S3 Express One Zone: Lớp lưu trữ mới cho ứng dụng AI/ML đòi hỏi độ trễ đọc/ghi siêu thấp (single-digit ms).
Học Yêu cầu / Tình huống trong đề thi Tùy chọn / Giải pháp chính xác Bẫy & Lưu ý mấu chốt
Yêu cầu luật định: cấm sửa/xóa file trong X năm (WORM) Bật S3 Object Lock (Compliance Mode) Compliance Mode: Kể cả tài khoản Root cũng không xóa được.
Governance Mode: Admin có quyền đặc biệt mới xóa được.
Phải bật Versioning trước.
Sao chép file sang Region khác để Disaster Recovery S3 Cross-Region Replication (CRR) Bắt buộc phải bật Versioning ở cả 2 bucket nguồn và đích.
Upload file lớn (> 100MB) bị gián đoạn mạng Dùng Multipart Upload Bắt buộc với file > 5GB, chia nhỏ upload song song, đứt đoạn nào tải lại đoạn đó.
Tăng tốc upload file từ xa trên toàn cầu vào S3 Bật S3 Transfer Acceleration Dữ liệu đi qua Edge Location gần nhất của CloudFront rồi chạy trên đường trục AWS.
Cấp quyền cho user ngoài tải 1 file tạm thời không cần IAM Tạo S3 Pre-signed URL Link có gắn sẵn token xác thực và thời hạn hết hạn (vài phút/giờ).
Chỉ cho phép CloudFront đọc S3, chặn gọi trực tiếp S3 URL Bật Origin Access Control (OAC) Chuẩn mới thay thế OAI cũ. Phối hợp với S3 Bucket Policy cho phép CloudFront ARN.

6. Cơ Sở Dữ Liệu Quan Hệ (Amazon RDS & Aurora)

Amazon RDS & Amazon Aurora
Domain 2 & 3 (Databases)

📖 Lý thuyết cốt lõi & Phân biệt kiến trúc:

  • RDS Multi-AZ Deployment: Tạo 1 instance Master và 1 instance Standby đồng bộ (Synchronous) ở AZ khác. Mục đích: High Availability & Tự động phục hồi lỗi (Failover). Standby không nhận truy vấn đọc/ghi. Multi-AZ KHÔNG tăng tốc độ đọc!
  • RDS Read Replicas: Nhân bản bất đồng bộ (Asynchronous) tối đa 15 bản sao. Mục đích: Tăng tốc độ đọc (Read-heavy). Có thể tạo cross-AZ hoặc cross-Region.
  • Kiến trúc Amazon Aurora: Cơ sở dữ liệu đám mây độc quyền của AWS (tương thích MySQL/PostgreSQL, nhanh gấp 5 lần MySQL). Dữ liệu tự động nhân bản thành 6 bản sao trải rộng trên 3 AZs. Chịu được mất trọn vẹn 1 AZ mà vẫn ghi/đọc bình thường.
  • Aurora Serverless v2: Tự động co giãn theo từng phân số ACU (Aurora Capacity Units) trong vài phần trăm giây. Phù hợp ứng dụng tải thất thường.
Học Yêu cầu / Tình huống trong đề thi Tùy chọn / Giải pháp chính xác Bẫy & Lưu ý mấu chốt
Hàng nghìn kết nối Lambda làm cạn kiệt connection pool DB Bật Amazon RDS Proxy Quản lý connection pooling tập trung, giảm thời gian failover Multi-AZ xuống 66%.
Đăng nhập database không cần lưu mật khẩu cứng trong code Bật IAM Database Authentication Dùng token xác thực ngắn hạn từ AWS STS (thời hạn 15 phút).
Khôi phục DB về đúng thời điểm trước khi bị drop nhầm bảng Dùng Point-In-Time Recovery (PITR) Kết hợp automated backup + transaction log để rollback về bất kỳ giây nào.
Đọc ghi dữ liệu toàn cầu với độ trễ replication dưới 1 giây Dùng Aurora Global Database 1 Primary Region (ghi/đọc) và tối đa 5 Secondary Regions (chỉ đọc). RTO < 1 phút khi cần failover thảm họa.
Đồng bộ dữ liệu Aurora sang Redshift mà KHÔNG viết ETL Glue Bật Aurora Zero-ETL Integration with Redshift 2026 Focus Dữ liệu giao dịch tự động replicate sang Data Warehouse trong vài giây.

7. NoSQL & Bộ Nhớ Đệm (DynamoDB & ElastiCache)

Amazon DynamoDB & Amazon ElastiCache
Domain 3 (In-Memory & NoSQL)

📖 Lý thuyết cốt lõi DynamoDB:

  • Bản chất: Cơ sở dữ liệu NoSQL Key-Value và Document hoàn toàn Serverless. Quy mô không giới hạn, độ trễ tính bằng mili-giây đơn chữ số (single-digit millisecond).
  • Primary Key: Partition Key (đơn vị băm) hoặc Hỗn hợp (Partition Key + Sort Key).
  • LSI (Local Secondary Index): Cùng Partition Key, khác Sort Key. Bắt buộc tạo ngay khi tạo bảng.
  • GSI (Global Secondary Index): Khác cả Partition Key và Sort Key. Tạo và xóa bất cứ lúc nào.
Học Yêu cầu / Tình huống trong đề thi Tùy chọn / Giải pháp chính xác Bẫy & Lưu ý mấu chốt
Đưa độ trễ đọc của DynamoDB từ mili-giây xuống micro-giây Bật DynamoDB Accelerator (DAX) In-memory cache native cho DynamoDB, không cần viết lại logic code ứng dụng.
Tự động dọn dẹp các session hết hạn sau 24h không tốn chi phí WCU Bật DynamoDB Time to Live (TTL) Chỉ định 1 attribute chứa timestamp epoch, DynamoDB tự xóa bản ghi quá hạn miễn phí.
Bắt mọi thao tác Insert/Update/Delete trên DynamoDB để gọi Lambda Bật DynamoDB Streams Cung cấp luồng dữ liệu thời gian thực các thay đổi để trigger Lambda hoặc replicate.
Cơ sở dữ liệu phân tán toàn cầu Multi-Region Active-Active Dùng DynamoDB Global Tables Đọc và ghi được ở bất kỳ Region nào, tự động sao chép 2 chiều. Yêu cầu bật Streams.
Cache dữ liệu phức tạp (Sorted sets, Hashes) cần Multi-AZ failover Dùng Amazon ElastiCache Redis Hỗ trợ cấu trúc dữ liệu, có sao lưu/khôi phục và tự động chuyển vùng khi sập.
Cache key-value đơn giản thuần in-memory đa luồng (multi-thread) Dùng Amazon ElastiCache Memcached Không hỗ trợ Multi-AZ failover hay backup.

8. Hàng Đợi & Kiến Trúc Tách Rời (SQS, SNS, EventBridge)

Decoupling & Event-Driven Architecture
Domain 2 (Resilient Core)
⚖️ So sánh kinh điển: SQS vs SNS vs EventBridge
  • Amazon SQS (Pull): Hàng đợi tin nhắn (Queue). Worker phải chủ động kéo tin nhắn về xử lý (Pull model). Dùng để **đệm tải (buffer)** chống quá tải hệ thống.
  • Amazon SNS (Push): Mô hình Pub/Sub. Bắn 1 tin nhắn đẩy ngay lập tức tới hàng nghìn subscriber (**Fan-out pattern**: đẩy tới nhiều SQS, Lambda, Email).
  • Amazon EventBridge (Bus): Event Bus kết nối các dịch vụ AWS và SaaS bên thứ 3. Có khả năng **lọc sự kiện dựa trên nội dung JSON payload** và lưu vết phát lại (**Archive & Replay**).
Học Yêu cầu / Tình huống trong đề thi Tùy chọn / Giải pháp chính xác Bẫy & Lưu ý mấu chốt
Tránh 2 worker cùng xử lý trùng 1 tin nhắn trong SQS Tăng Visibility Timeout Thời gian tin nhắn bị ẩn với worker khác trong khi đang được xử lý (mặc định 30s).
Giảm số lượng request rỗng và tiết kiệm chi phí SQS Bật Long Polling (WaitTimeSeconds > 0) Worker đợi tối đa 20s cho tới khi có tin mới tới thay vì trả về ngay lập tức.
Đảm bảo tin nhắn xử lý đúng thứ tự từng khách và không trùng lặp SQS FIFO Queue + MessageGroupID Tên queue phải có đuôi .fifo. MessageGroupID gom tuần tự theo khách; MessageDeduplicationID chống trùng trong 5 phút.
Tin nhắn xử lý lỗi nhiều lần làm nghẽn hàng đợi Cấu hình Dead-Letter Queue (DLQ) Đặt tham số maxReceiveCount, lỗi vượt ngưỡng sẽ tự đẩy sang DLQ.

🎯 6 Chủ đề phân loại thí sinh giỏi (750 điểm) vs Thí sinh xuất sắc (900+ điểm):

  • 1. Hybrid DNS với Route 53 Resolver:
    • Inbound Endpoint: Cho phép máy chủ On-premise gửi truy vấn DNS vào AWS để phân giải domain riêng trong VPC (Route 53 Private Hosted Zone).
    • Outbound Endpoint: Cho phép máy ảo EC2 trong VPC gửi truy vấn DNS ngược về Data Center On-premise để phân giải domain nội bộ công ty (`corp.local`).
  • 2. S3 Bucket Key (Tối ưu 99% chi phí KMS): Khi mã hóa hàng triệu file trên S3 bằng KMS (SSE-KMS), số lượng request gọi KMS rất lớn gây đội chi phí. Bật S3 Bucket Key cho phép S3 tạo data key ở cấp bucket, giảm tới 99% chi phí KMS request.
  • 3. Bảo mật Cross-Account S3 + KMS: Khi Account A cấp quyền cho Account B đọc file mã hóa trong S3, cần 3 điều kiện: (1) S3 Bucket Policy cho phép Account B, (2) IAM Policy của User ở Account B cho phép đọc S3 & giải mã KMS, và (3) KMS Key Policy ở Account A bắt buộc phải cho phép Account B giải mã. Thiếu KMS Key Policy sẽ bị Access Denied ngay lập tức.
  • 4. Chống lỗi Confused Deputy với IAM sts:ExternalId: Khi bạn thuê 1 công ty SaaS bên thứ 3 quản lý tài khoản AWS của bạn qua IAM Role, hacker có thể lợi dụng SaaS đó để truy cập trái phép. Giải pháp: Bắt buộc cấu hình thêm Condition: { "StringEquals": { "sts:ExternalId": "unique-client-secret" } } trong Trust Policy của Role.
  • 5. Kết nối Direct Connect đa vùng (DXGW): Dùng Direct Connect Gateway (DXGW) để 1 đường Direct Connect vật lý có thể kết nối tới nhiều VPC ở các Region khác nhau trên toàn cầu.
    • Private VIF: Nối vào 1 VPC hoặc DXGW.
    • Transit VIF: Nối vào AWS Transit Gateway (kết nối hàng trăm VPC).
  • 6. Ma trận 4 chiến lược Disaster Recovery (RPO & RTO):
    • Backup & Restore: RPO/RTO tính bằng Giờ/Ngày $\rightarrow$ Chi phí rẻ nhất.
    • Pilot Light: Database đồng bộ liên tục, chỉ bật server EC2 khi có sự cố $\rightarrow$ RPO/RTO tính bằng chục Phút.
    • Warm Standby: Hệ thống thu nhỏ (min-capacity) chạy sẵn 24/7 ở Region 2, khi sập chỉ cần scale to lên $\rightarrow$ RPO/RTO tính bằng Phút.
    • Multi-Region Active-Active: Chạy full tải cả 2 Region song song $\rightarrow$ RPO/RTO tính bằng Giây (gần bằng 0), đắt nhất.

Yêu cầu RTO dưới 5 phút, RPO gần bằng 0 nhưng chi phí vừa phải Chọn chiến lược Warm Standby Pilot Light mất lâu hơn để bật compute; Active-Active chi phí quá đắt gấp đôi.

16. Cây Quyết Định Bắt Nhanh Đáp Án 10s CHEAT SHEET

🎯 Tư duy loại suy phản xạ nhanh: Xác định đúng 1 trong 4 mục tiêu tối thượng dưới đây trong đề bài để bắt ngay bộ dịch vụ kiến trúc tương ứng mà không cần đọc dài dòng! Nhấp vào các mã dịch vụ để sao chép nhanh.
💰
Chi Phí Rẻ Nhất
Most Cost-Effective
EC2 Compute
Chọn Spot Instances (cho batch job chịu gián đoạn) hoặc Savings Plans / Reserved Instances (chạy liên tục 24/7).
Storage
S3 Intelligent-Tiering (dữ liệu mẫu truy cập không rõ ràng) → Lifecycle sang Glacier Deep Archive (lưu trữ kiểm toán lâu năm).
Network
Chọn VPC Gateway Endpoint cho S3 & DynamoDB (Miễn phí 100%, không tốn tiền qua NAT Gateway).
⚡
Ít Công Bảo Trì Nhất
Least Operational Overhead
Serverless First
Ưu tiên tuyệt đối: AWS Lambda, AWS Fargate, Aurora Serverless v2, Amazon EventBridge (AWS lo OS & patching).
Tự Động Hóa
S3 Lifecycle Policies, SSM Session Manager (thay thế Bastion host), Secrets Manager Auto-rotation.
🛡️
Khả Năng Chịu Lỗi Cao Nhất
High Availability / Fault Tolerant
Database Tier
Bật Multi-AZ (RDS / Aurora) tự động đồng bộ sang Standby ở AZ khác, tự failover trong 60-120 giây.
Compute Tier
Auto Scaling Group (ASG) kết hợp ALB trải dài tối thiểu trên 2-3 Availability Zones (AZs).
Decoupled
Kiến trúc tách rời độc lập qua hàng đợi Amazon SQS buffer tải hoặc Amazon SNS Fanout.
🚀
Tốc Độ Siêu Tốc
Sub-millisecond Latency / Caching
Cache Cho Ứng Dụng
Amazon ElastiCache (Redis) đặt đệm trước RDS để giải tỏa tải đọc database.
Cache Cho DynamoDB
DynamoDB Accelerator (DAX) đưa tốc độ đọc từ milliseconds về microseconds (10x faster).
Toàn Cầu
Amazon CloudFront (cho web/nội dung tĩnh) hoặc AWS Global Accelerator (cho IP Anycast & non-HTTP).
